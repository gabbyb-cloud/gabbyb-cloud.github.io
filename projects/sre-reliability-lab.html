System scope

The application stays small so operating behavior can be isolated. Readiness, normal workload behavior, application-level failure, telemetry, and recovery are treated as separate signals.

The service exposes /health, /ready, /work, and /metrics, allowing each part of the request path to be tested independently.

How the system works

Traffic reaches the FastAPI workload through a Kubernetes Service. Application behavior is separated from pod health so Prometheus and Grafana can detect a reachable service that is returning errors.

Tooling choices

  • Docker: creates a repeatable application image.
  • Kubernetes + Helm: manage workload deployment, probes, configuration, and rollout behavior.
  • Prometheus + Grafana: provide metrics, PromQL queries, alerting, and visualization.
  • Terraform: adopts and manages the existing sre-lab namespace as infrastructure state.
  • GitHub Actions: validates Python, Docker, Helm, and Terraform changes before they reach the protected branch.
Key decision Keep readiness healthy during injected application failure.

This keeps user-facing 5xx errors separate from pod availability, so monitoring can observe a reachable but degraded service instead of Kubernetes immediately removing it from view.

Failure measurement

The availability SLO is 99% for successful /work requests. The SLI compares successful 2xx responses with total /work requests over the measurement window.

The HighErrorRate alert fires when more than 20% of /work requests are 5xx over 2 minutes for at least 1 minute. That window fits the local, low-traffic environment and makes the full alert lifecycle practical to test.

Failure exercise

With FAIL_MODE=true, /work returns HTTP 500 while /ready stays at HTTP 200. That lets me test an application failure without making the pod unavailable.

01 Healthy baseline

Readiness is healthy and normal /work requests succeed.

02 Failure injected

FAIL_MODE=true causes /work to return HTTP 500 while /ready remains HTTP 200.

03 Alert transitions

Sustained errors move HighErrorRate from Inactive to Pending to Firing.

04 Recovery executed

Failure mode is disabled and the deployment rollout is checked rather than assuming the change succeeded.

05 Recovery verified

Application behavior, metrics, targets, and alert state are rechecked until the alert resolves.

Lessons from the lab

The important part was connecting deployment state, application behavior, telemetry, alerting, recovery, and verification. The service can look healthy at the pod level while still failing at the application level.

This lab is not intended to make throughput or latency claims. The evidence is functional: the failure can be injected, detected with application-level telemetry, recovered, and verified afterward.

Limits of the lab

The lab demonstrates SRE concepts in a reproducible local environment. A production platform would still require managed secrets, external alert routing, high-availability design, production telemetry, stronger security controls, image registry workflows, capacity planning, cloud IAM, and environment-specific networking and infrastructure.

The next useful extensions would be automated failure scenarios, distributed tracing across a dependency boundary, and a small cloud deployment that adds IAM and managed networking while preserving the same reliability workflow.
