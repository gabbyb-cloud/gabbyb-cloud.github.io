SRE Reliability Lab

01 / Problem

Deployment was only the starting point.

The application is intentionally small because the project is about operating the service around it. The lab focuses on the questions that matter after deployment: Is the service ready? What does normal behavior look like? Which signal proves user-facing failure? When should an alert fire? How should recovery happen, and how do I prove the system actually returned to normal?

The service exposes /health, /ready, /work, and /metrics endpoints so health, workload behavior, telemetry, and recovery can be tested independently.

02 / Architecture

The architecture is deliberately small and operationally observable.

Traffic reaches a FastAPI workload through a Kubernetes Service. Helm manages the application resources, Kubernetes probes report liveness and readiness, and Prometheus discovers application metrics through a ServiceMonitor. Grafana visualizes behavior, while a Prometheus alert rule detects sustained error-rate degradation.

TrafficClient → Kubernetes Service → FastAPI Pod
TelemetryPod /metrics → ServiceMonitor → Prometheus
VisibilityPrometheus → Grafana dashboards
ResponsePrometheus alert → investigate → recover → verify
03 / Design decisions

Each tool has a specific operating job.

  • Docker: creates a repeatable application image.
  • Kubernetes + Helm: manage workload deployment, probes, configuration, and rollout behavior.
  • Prometheus + Grafana: provide metrics, PromQL queries, alerting, and visualization.
  • Terraform: adopts and manages the existing sre-lab namespace as infrastructure state.
  • GitHub Actions: validates Python, Docker, Helm, and Terraform changes before they reach the protected branch.

A key design choice is keeping readiness healthy during injected application failure. That separates user-facing 5xx errors from pod availability and allows the monitoring system to observe a reachable but degraded service.

04 / Reliability target

The monitoring starts with a measurable objective.

The lab defines a 99% availability SLO for successful /work requests. The SLI compares successful 2xx responses with total /work requests over the measurement window.

The HighErrorRate alert fires when more than 20% of /work requests are 5xx over a 2-minute window for at least 1 minute. The short window is intentional for a low-traffic local lab; it makes the full alert lifecycle practical to exercise while keeping the alert tied to application behavior rather than pod health alone.

05 / Failure drill

I deliberately degraded the workload without making the pod unavailable.

With FAIL_MODE=true, /work returns HTTP 500 while /ready continues returning HTTP 200. This creates an application-level incident that Kubernetes does not hide by immediately removing the pod from traffic.

Sustained failing requests drive the alert through Inactive → Pending → Firing. Recovery begins by disabling failure mode, then verifying the deployment rollout and application behavior rather than assuming the configuration change succeeded.

06 / Verification

Recovery is not complete until multiple signals agree.

KubernetesDeployment rollout and pod readiness verified
Application/ready and /work behavior rechecked
MonitoringPrometheus target and error metrics verified
AlertingHighErrorRate returned to resolved/inactive

The Terraform-managed namespace was also reconciled successfully with No changes. Your infrastructure matches the configuration. The repository includes a runbook and a blameless postmortem so operational response is documented alongside the code and infrastructure.

07 / What this proved

The useful evidence is the operating loop, not the tool list.

The completed exercise demonstrates that I can connect deployment state, application behavior, telemetry, alerting, incident response, and verification into one repeatable reliability workflow: Observe → Diagnose → Recover → Verify → Document.

The project intentionally makes no throughput or latency claims. Its evidence is functional: the service can be degraded in a controlled way, the failure can be detected through application-level telemetry, recovery can be executed, and the system can be verified afterward.

08 / Production boundary

Local reliability evidence is not production equivalence.

The lab demonstrates SRE concepts in a reproducible local environment. A production platform would still require managed secrets, external alert routing, high-availability design, production telemetry, stronger security controls, image registry workflows, capacity planning, cloud IAM, and environment-specific networking and infrastructure.

The next useful extensions would be automated failure scenarios, distributed tracing across a dependency boundary, and a small cloud deployment that adds IAM and managed networking while preserving the same reliability workflow.
