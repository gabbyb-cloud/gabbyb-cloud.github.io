SRE Reliability Lab

A complete local reliability lab for practicing Kubernetes operations, infrastructure automation, observability, SLOs, alerting, controlled failure and recovery, and incident response without paid cloud infrastructure.

PythonFastAPIDockerKubernetesHelmTerraformPrometheusGrafana

01 · Overview

The lab centers on a FastAPI service with /health, /ready, /work, and /metrics endpoints. The service is containerized with Docker, deployed to a local kind Kubernetes cluster through Helm, observed with Prometheus and Grafana, and supported by Terraform-managed infrastructure state plus operational documentation.

02 · Problem

The goal was to move beyond learning infrastructure tools individually and operate a small system end to end: deploy it, determine whether it is ready, observe it, define a reliability target, detect failure, recover it, and document the response.

03 · Architecture

The environment is intentionally local-first: FastAPI → Docker → kind/Kubernetes, packaged with Helm. Prometheus scrapes application metrics, Grafana provides visibility, and Terraform manages the selected Kubernetes infrastructure resource. This keeps the lab reproducible and free while exposing the same operational concepts used in larger environments.

04 · Technical Decisions

  • FastAPI keeps application complexity small so the reliability work remains the focus.
  • python:3.12-slim provides a straightforward application image.
  • kind provides a disposable local Kubernetes cluster without paid cloud infrastructure.
  • Helm packages and deploys the application consistently.
  • Terraform is deliberately minimal rather than pretending the entire environment is infrastructure-as-code.
  • Prometheus and Grafana provide metrics collection and operational visibility.

05 · Reliability / Failure Handling

Separate health and readiness endpoints distinguish process health from readiness to receive traffic. The lab includes a controlled failure and recovery exercise, verifies service recovery, and documents the operational response in a runbook and a short blameless postmortem.

06 · Observability

The application exposes Prometheus-compatible request metrics. Prometheus scraping was verified, Grafana is available for visualization, and the lab includes one availability SLO plus a HighErrorRate alert whose Pending → Firing → resolved behavior was exercised during validation.

07 · Testing & Validation

Validation covered application readiness and work endpoints, Prometheus target and metric visibility, Helm linting, Terraform plan state, alert-state behavior, Git state, and post-failure recovery. The completed lab also includes RUNBOOK.md and POSTMORTEM.md as operational artifacts.

08 · Results

The finished lab demonstrates an end-to-end local SRE workflow: package and deploy a service to Kubernetes, observe it, define a reliability objective, trigger and detect an error condition, recover the service, and document what happened. It is intentionally a local reliability lab rather than a claim of operating a production Kubernetes platform.

09 · Lessons Learned

Reliability becomes much more concrete when deployment, metrics, alert behavior, recovery, and documentation are treated as one operating loop instead of separate tools. Local Kubernetes also exposes image distribution, pod state, readiness, and deployment behavior without a managed service hiding those details.

10 · What I Would Change for Production

A production implementation would add a real image registry, managed secrets, external alert routing, security hardening, high-availability design, environment-specific infrastructure, and production capacity planning. Those concerns are intentionally outside the scope of this local lab.
