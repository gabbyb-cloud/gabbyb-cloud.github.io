SRE Reliability Lab

A local reliability lab built to practice the complete operating loop: deploy, observe, define a reliability target, detect failure, recover, verify, and document.

01 / Problem

Deployment was only the starting point.

The application is intentionally small because the project is about operating the service around it. The lab focuses on questions an SRE needs to answer: Is the service ready? What is normal behavior? What signal shows failure? What should alert? How do I recover it, and how do I prove recovery worked?

The service exposes /health, /ready, /work, and /metrics endpoints so each part of that operating loop can be tested directly.

02 / Operating model

Each tool has a specific operating job.

FastAPI is containerized with Docker, loaded into a kind cluster, and deployed through Helm. Kubernetes probes track liveness and readiness. Prometheus discovers the application through a ServiceMonitor, Grafana visualizes service behavior, and Terraform manages the existing lab namespace as explicit infrastructure state.

  • Docker: repeatable application image.
  • Kubernetes + Helm: service deployment, probes, configuration, and rollout behavior.
  • Prometheus + Grafana: metrics, queries, alerting, and visualization.
  • Terraform: adoption and management of an existing Kubernetes namespace.
  • GitHub Actions: validation of Python, Docker, Helm, and Terraform changes.
03 / Reliability target

A measurable target gives the monitoring context.

The lab defines a 99% availability SLO for successful /work requests. The corresponding SLI compares successful 2xx requests with total requests over the local test window.

The HighErrorRate alert is configured for sustained elevated 5xx responses, turning application behavior into an actionable reliability signal instead of relying only on pod health.

04 / Failure drill

I deliberately broke the workload while keeping the service reachable.

With controlled failure mode enabled, /work returns HTTP 500 while /ready remains healthy. That keeps the pod available long enough for Prometheus to observe application-level failure instead of Kubernetes simply removing the workload from traffic.

The alert was exercised through its lifecycle from inactive to pending to firing. Failure mode was then disabled, the rollout was verified, service behavior was rechecked, and the alert was observed returning to a resolved state.

05 / Verification

Recovery is not complete until it is verified.

KubernetesDeployment rollout and pod readiness checked
Application/ready and /work behavior rechecked

The repository also includes a runbook and blameless postmortem so the operational response is documented alongside the infrastructure and code.

06 / Takeaway

The useful skill is the loop, not the tool list.

This project reinforced a repeatable reliability workflow: Observe → Diagnose → Recover → Verify → Document. Kubernetes, Prometheus, Grafana, Helm, and Terraform matter because they support that workflow—not because simply installing them demonstrates reliability engineering.

07 / Boundary

Local reliability evidence is not production equivalence.

The lab demonstrates SRE concepts in a reproducible local environment. A production platform would still require managed secrets, external alert routing, high-availability design, production telemetry, stronger security controls, image registry workflows, capacity planning, and environment-specific infrastructure.
