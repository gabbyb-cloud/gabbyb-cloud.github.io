01 / System goal

Operate the service, not just deploy it.

The application is intentionally small. The engineering work is the operating loop around it: package the service, deploy it, determine whether it is ready, observe behavior, define a reliability target, detect failure, recover the service, and document what happened.

The service exposes /health, /ready, /work, and /metrics endpoints so infrastructure and reliability behavior remain visible and testable.

02 / Architecture

A deliberately small reliability stack.

FastAPI is containerized with Docker and deployed into a local kind Kubernetes cluster through Helm. Prometheus scrapes application metrics, Grafana provides visualization, and Terraform manages a selected Kubernetes infrastructure resource rather than pretending the entire environment is infrastructure-as-code.

  • Docker provides a repeatable application image.
  • kind keeps Kubernetes local and disposable.
  • Helm packages deployment configuration consistently.
  • Prometheus and Grafana expose system behavior.
  • Terraform is used narrowly where it adds explicit state management.
03 / Reliability controls

Failure is part of the test plan.

Separate liveness and readiness endpoints distinguish process health from readiness to receive traffic. The lab defines a 99% availability SLO and includes a HighErrorRate Prometheus alert.

A controlled HTTP 500 exercise was used to observe the alert move through Pending and Firing states, recover the application, and verify alert resolution rather than stopping at alert configuration.

04 / Validation

Evidence is checked across the operating path.

Validation covers application readiness, the work endpoint, Prometheus target and metric visibility, Helm linting, Terraform state and formatting, alert behavior, and post-failure recovery. GitHub Actions validates Python, Docker, Helm, and Terraform changes.

05 / Engineering takeaway

Reliability becomes concrete when the loop is complete.

The most useful part of the lab is not any one tool. It is treating deployment, metrics, alert behavior, failure recovery, and documentation as one connected operating system. Local Kubernetes also makes pod state, readiness, image distribution, and rollout behavior visible without a managed platform hiding those details.

06 / Production boundary

Local evidence is not production equivalence.

This project demonstrates reliability concepts in a reproducible local environment. A production implementation would still require a real image registry, managed secrets, external alert routing, stronger security controls, high-availability design, environment-specific infrastructure, capacity planning, and production telemetry.

The project is intentionally presented as a reliability engineering lab, not as a claim of operating a production Kubernetes platform.
