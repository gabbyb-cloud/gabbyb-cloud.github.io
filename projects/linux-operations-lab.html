System scope

The service is intentionally small so Linux behavior stays isolated. When an endpoint becomes unavailable, the investigation checks process state, systemd, the expected socket, file permissions, routing or DNS, and host resource pressure before changing anything.

That evidence identifies the failing layer instead of jumping directly to a restart or code change.

Troubleshooting method

The visible symptom is the starting point, followed by checks of service state, logs, sockets, networking, permissions, and host resources. After a targeted change, both the service and application are checked again.

Failure scenarios

A small Python HTTP service is managed through a checked-in systemd unit. A deliberate service stop provides a controlled failure, with investigation working outward from the failed request rather than assuming the root cause.

01 Symptom observed

The user-visible failure is established before any changes are made.

02 Service inspected

systemctl status confirms service ownership and current state.

03 Logs reviewed

journalctl -u linux-lab exposes service history and failure evidence.

04 Socket checked

ss -lntp confirms whether the expected TCP listener is present.

05 Recovery verified

After the targeted fix, systemctl, ss, and curl are used together to confirm recovery.

Operating rule A restart is a corrective action, not proof of recovery.

Recovery is complete only when service state, socket state, and application behavior agree.

Permissions

Users, groups, ownership, and mode bits are used to reproduce access failures intentionally. Ownership and permissions are inspected before changes so an access problem is not mistaken for an application defect.

Networking

Interface state, routing, listening sockets, DNS resolution, and direct HTTP connectivity are checked separately. Each answers a different question, helping distinguish a service that is not listening from a host that cannot route traffic or resolve names.

Host health

CPU count, load, memory usage, disk usage, and running processes are included so the troubleshooting path covers the operating environment beneath the application.

CPUCPU count · uptime · loadEstablishes basic host capacity and load context.
MemoryMemory usage · top consumersHelps identify host-level pressure and heavy processes.
StorageRoot filesystem usageChecks whether disk pressure could affect service behavior.
Service statelinux-lab systemd statusKeeps application state in the same operational snapshot.

Automation

A Bash health script collects a consistent first-pass snapshot: hostname, CPU count, uptime and load, memory usage, root filesystem usage, high-memory processes, and the linux-lab service state.

It does not replace investigation or monitoring; it makes the first evidence-gathering step faster and more repeatable.

Lessons from the lab

Containers and Kubernetes add abstraction, but processes, sockets, permissions, logs, networking, and resource usage still exist underneath them. Working through those layers directly gives me a clearer way to isolate failures before moving to higher-level platform systems.

The same checks make higher-level SRE and platform troubleshooting easier to reason about because failures can be traced back to the layer where they begin.

Limits of the lab

The environment runs locally on Ubuntu under WSL2, and the checked-in systemd unit must be adapted for another host. The project intentionally does not claim centralized logging, production hardening, configuration management, fleet orchestration, alerting, or multi-host automation.

The next useful step would be repeating the same exercises on a small Linux VM or cloud instance and adding smoke tests for the example service and health script.
