What I built

The service is intentionally small so I can isolate Linux behavior. When an endpoint becomes unavailable, I check process state, systemd, the expected socket, file permissions, routing or DNS, and host resource pressure before changing anything.

I use that evidence to identify the failing layer instead of jumping directly to a restart or code change.

How I troubleshoot

I start with the visible symptom, then narrow the failure by checking service state, logs, sockets, networking, permissions, and host resources. After a targeted change, I check the service and application again.

What I tested

A small Python HTTP service is managed through a checked-in systemd unit. I deliberately stop the service, then work outward from the failed request rather than assuming the root cause.

01 Symptom observed

I establish the user-visible failure before making any changes.

02 Service inspected

systemctl status to confirm service ownership and current state.

03 Logs reviewed

journalctl -u linux-lab to inspect service history and failure evidence.

04 Socket checked

ss -lntp to confirm whether the expected TCP listener is present.

05 Recovery verified

After the targeted fix, I use systemctl, ss, and curl together to confirm recovery.

Operating rule A restart is a corrective action, not proof of recovery.

I consider recovery complete only when service state, socket state, and application behavior agree.

Permissions

I use users, groups, ownership, and mode bits to reproduce access failures intentionally. I inspect ownership and permissions before making changes so an access problem is not mistaken for an application defect.

Networking

I separate interface state, routing, listening sockets, DNS resolution, and direct HTTP connectivity. Each check answers a different question, which helps me distinguish a service that is not listening from a host that cannot route traffic or resolve names.

Host health

I inspect CPU count, load, memory usage, disk usage, and running processes so the troubleshooting path includes the operating environment beneath the application.

CPUCPU count · uptime · loadEstablishes basic host capacity and load context.
MemoryMemory usage · top consumersHelps identify host-level pressure and heavy processes.
StorageRoot filesystem usageChecks whether disk pressure could affect service behavior.
Service statelinux-lab systemd statusKeeps application state in the same operational snapshot.

What I automated

I use a Bash health script to collect a consistent first-pass snapshot: hostname, CPU count, uptime and load, memory usage, root filesystem usage, high-memory processes, and the linux-lab service state.

It does not replace investigation or monitoring; it makes the first evidence-gathering step faster and more repeatable.

What I learned

Containers and Kubernetes add abstraction, but processes, sockets, permissions, logs, networking, and resource usage still exist underneath them. Working through those layers directly gives me a clearer way to isolate failures before moving to higher-level platform systems.

The same checks make higher-level SRE and platform troubleshooting easier to reason about because I can trace the failure back to the layer where it begins.

Limits of the lab

The environment runs locally on Ubuntu under WSL2, and the checked-in systemd unit must be adapted for another host. The project intentionally does not claim centralized logging, production hardening, configuration management, fleet orchestration, alerting, or multi-host automation.

The next useful step would be repeating the same exercises on a small Linux VM or cloud instance and adding smoke tests for the example service and health script.
