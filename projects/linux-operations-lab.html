Case Study 02 · Linux Operations & Troubleshooting

Linux Operations Lab

A hands-on Linux environment built to practice a repeatable operations loop: observe the symptom, inspect the host, isolate the failure, recover the service, verify the fix, and automate repeated checks.

01 / Problem

A failed request can come from more than the application.

The lab keeps the application simple so troubleshooting stays focused on the operating system. When a service is unavailable, the useful question is not only “is the code broken?” but also whether the process is running, systemd is managing it, the expected port is listening, permissions are correct, networking is healthy, and the host has the resources it needs.

02 / Troubleshooting model

Inspect before changing the system.

The exercises follow a consistent workflow: start with the visible symptom, collect evidence, isolate the affected layer, apply the smallest corrective action, and verify the result.

  • Observe: failed HTTP request, stopped service, denied access, missing listener, or connectivity problem.
  • Inspect: service state, logs, processes, sockets, routes, permissions, and host resources.
  • Isolate: application, service manager, process, permissions, networking, or host resources.
  • Recover: make the smallest targeted correction.
  • Verify: confirm service state, listener state, and application response.
03 / Service incident

Break the service, investigate it, then prove recovery.

A small Python HTTP service is managed through a checked-in systemd unit. The lab intentionally stops the service to create an availability failure and then walks through the recovery path.

Statesystemctl status checks service health
Logsjournalctl provides service history and errors
Listenerss confirms the expected TCP port
Applicationcurl verifies the HTTP response

The important distinction is that restarting the service is an action; confirming process state, port state, and HTTP behavior is the verification that recovery succeeded.

04 / Permissions & networking

Failure domains are easier to diagnose when they are separated.

Controlled permission failures make users, groups, ownership, and mode bits visible during troubleshooting. The networking exercises similarly separate interface state, routing, listening sockets, DNS resolution, and application connectivity instead of treating “the network” as one problem.

This creates a more disciplined path from host state to application behavior and reduces guesswork during troubleshooting.

05 / Host health

System state matters when services degrade.

The lab inspects CPU, memory, disk usage, load, and running processes so service troubleshooting includes the health of the host underneath the application.

Those checks help answer whether the service problem is isolated to the application or related to broader resource pressure on the system.

06 / Automation

Repeated diagnostics became a small operational tool.

A Bash health-check script collects a consistent first-pass system snapshot: hostname, CPU count, uptime and load, memory usage, filesystem usage, highest-memory processes, and the linux-lab systemd service state.

The script does not replace investigation. It makes the initial evidence collection faster and more repeatable.

07 / Takeaway

Linux fundamentals make higher-level systems easier to reason about.

Containers and Kubernetes add abstraction, but processes, sockets, permissions, logs, networking, and resource usage still sit underneath those platforms. Practicing these fundamentals directly makes platform and SRE troubleshooting more concrete.

Observe → Diagnose → Recover → Verify → Automate is the operating pattern carried from this lab into the rest of the portfolio.

08 / Boundary

This is an operations lab, not a production fleet.

The checked-in systemd unit reflects the local lab environment and must be adapted for another host. The project intentionally does not claim centralized logging, production hardening, configuration management, fleet orchestration, or large-scale automation.
