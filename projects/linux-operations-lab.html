Case Study 02 · Linux Operations & Troubleshooting

Linux Operations Lab

A hands-on Linux environment built to practice a disciplined operations loop: observe the symptom, inspect the host, isolate the failing layer, apply the smallest fix, verify recovery, and automate repeatable checks.

01 / Problem

A failed request can originate below the application layer.

The service is intentionally small so troubleshooting stays focused on Linux behavior. When an endpoint becomes unavailable, the useful questions are broader than “is the code broken?”: Is the process running? Is systemd managing it? Is the expected socket listening? Are file permissions correct? Is routing or DNS involved? Is the host under resource pressure?

The lab was built to practice answering those questions with evidence instead of jumping directly to restarts or code changes.

02 / Troubleshooting model

Inspect before changing the system.

The exercises follow the same workflow across service, permission, network, and resource problems: begin with the visible symptom, collect evidence by layer, isolate the failure domain, make the smallest corrective change, then verify from multiple angles.

  • Observe: failed HTTP request, stopped service, access denial, missing listener, or connectivity symptom.
  • Inspect: service state, logs, processes, sockets, permissions, routes, DNS, and host resources.
  • Isolate: distinguish application, service manager, process, filesystem, network, or resource failure.
  • Recover: make the smallest targeted correction.
  • Verify: confirm service state, listener state, and HTTP behavior.
03 / Service incident

A controlled outage turns the troubleshooting workflow into evidence.

A small Python HTTP service is managed through a checked-in systemd unit. The lab deliberately stops the service, then works outward from the symptom rather than assuming the root cause.

Service managersystemctl status confirms ownership and current state
Logsjournalctl provides service history and failure evidence
Socketss confirms whether TCP :8000 is listening
Applicationcurl verifies the service can answer an HTTP request

Restarting the service is only the corrective action. Recovery is considered complete only after systemd state, socket state, and application behavior agree that the service is healthy again.

04 / Permissions

Access failures are diagnosed as filesystem and identity problems first.

Controlled permission exercises use users, groups, ownership, and mode bits to reproduce access failures intentionally. Ownership and permissions are inspected before changes are made so an access problem is not misdiagnosed as an application defect.

This reinforces a simple operating principle: identify the layer that denies access before modifying the software that happens to be affected by it.

05 / Networking

“The network is down” is broken into testable questions.

The networking exercises separate interface state, routing, listening sockets, DNS resolution, and direct HTTP connectivity. Each check answers a different question, which makes it easier to distinguish a service that is not listening from a host that cannot route traffic or resolve names.

This layered approach reduces guesswork and creates a clearer path from host state to application reachability.

06 / Host health

Service degradation can be a host problem.

The lab inspects CPU count, load, memory usage, disk usage, and running processes so troubleshooting includes the operating environment beneath the application.

Those checks help distinguish an isolated service failure from broader resource pressure that could affect multiple processes on the host.

07 / Automation

Repeated evidence collection became a lightweight operational tool.

A Bash health script collects a consistent first-pass snapshot: hostname, CPU count, uptime and load, memory usage, root filesystem usage, high-memory processes, and the linux-lab service state.

The script is intentionally small. It does not replace investigation or monitoring; it makes the initial evidence-gathering step faster and more repeatable.

09 / Takeaway

Linux fundamentals make platform failures easier to reason about.

Containers and Kubernetes add abstraction, but processes, sockets, permissions, logs, networking, and resource usage still exist underneath those platforms. Practicing these layers directly makes higher-level SRE and platform troubleshooting more concrete.

Observe → Diagnose → Recover → Verify → Automate is the operating pattern this lab contributes to the rest of the portfolio.

10 / Production boundary

This is an operations lab, not a production Linux fleet.

The original environment runs locally on Ubuntu under WSL2, and the checked-in systemd unit must be adapted for another host. The project intentionally does not claim centralized logging, production hardening, configuration management, fleet orchestration, alerting, or multi-host automation.

The next useful step would be repeating the same exercises on a small Linux VM or cloud instance and adding smoke tests for the example service and health script.
