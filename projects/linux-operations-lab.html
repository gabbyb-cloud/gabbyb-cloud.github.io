Case Study 02 · Linux Operations & Troubleshooting

Linux Operations Lab

A hands-on Linux environment built around a disciplined troubleshooting loop: observe the symptom, inspect the host, isolate the failing layer, apply the smallest fix, verify recovery, and automate repeatable checks.

01 / Problem

A failed request can originate below the application layer.

The service is intentionally small so troubleshooting stays focused on Linux behavior. When an endpoint becomes unavailable, the useful questions are broader than “is the code broken?”: Is the process running? Is systemd managing it? Is the expected socket listening? Are file permissions correct? Is routing or DNS involved? Is the host under resource pressure?

The lab was built to answer those questions with evidence instead of jumping directly to restarts or code changes.

02 / Troubleshooting model

Inspect before changing the system.

The same workflow is used across service, permission, networking, and resource problems: begin with the visible symptom, collect evidence by layer, isolate the failure domain, make the smallest corrective change, then verify from multiple angles.

03 / Service incident

Run a service, break it, inspect it, and recover it.

A small Python HTTP service is managed through a checked-in systemd unit. The lab deliberately stops the service, then works outward from the symptom rather than assuming the root cause.

01 Symptom observed

An HTTP request fails, establishing the user-visible problem before any changes are made.

02 Service inspected

systemctl status confirms whether systemd owns the service and shows its current state.

03 Logs reviewed

journalctl -u linux-lab provides service history and failure evidence.

04 Socket checked

ss -lntp confirms whether the expected TCP listener is present.

05 Recovery verified

After the targeted fix, systemctl, ss, and curl are used together to confirm recovery.

Operating rule A restart is a corrective action, not proof of recovery.

Recovery is only complete when service state, socket state, and application behavior all agree.

04 / Permissions

Access failures become easier to debug when ownership is explicit.

Controlled permission exercises use users, groups, ownership, and mode bits to reproduce access failures intentionally. Ownership and permissions are inspected before changes are made so an access problem is not misdiagnosed as an application defect.

05 / Networking

Trace connectivity from interface state to application response.

The networking exercises separate interface state, routing, listening sockets, DNS resolution, and direct HTTP connectivity. Each check answers a different question, which makes it easier to distinguish a service that is not listening from a host that cannot route traffic or resolve names.

06 / Host health

Service degradation can be a host problem.

The lab inspects CPU count, load, memory usage, disk usage, and running processes so troubleshooting includes the operating environment beneath the application.

CPUCPU count · uptime · loadEstablishes basic host capacity and load context.
MemoryMemory usage · top consumersHelps identify host-level pressure and heavy processes.
StorageRoot filesystem usageChecks whether disk pressure could affect service behavior.
Service statelinux-lab systemd statusKeeps application state in the same operational snapshot.
07 / Automation

Repeated inspection became a lightweight operational tool.

A Bash health script collects a consistent first-pass snapshot: hostname, CPU count, uptime and load, memory usage, root filesystem usage, high-memory processes, and the linux-lab service state.

The script does not replace investigation or monitoring; it makes the first evidence-gathering step faster and more repeatable.

09 / Takeaway

Linux fundamentals make platform failures easier to reason about.

Containers and Kubernetes add abstraction, but processes, sockets, permissions, logs, networking, and resource usage still exist underneath those platforms. Practicing these layers directly makes higher-level SRE and platform troubleshooting more concrete.

Observe → Diagnose → Recover → Verify → Automate is the operating pattern this lab contributes to the rest of the portfolio.

10 / Production boundary

This is an operations lab, not a production Linux fleet.

The environment runs locally on Ubuntu under WSL2, and the checked-in systemd unit must be adapted for another host. The project intentionally does not claim centralized logging, production hardening, configuration management, fleet orchestration, alerting, or multi-host automation.

The next useful step would be repeating the same exercises on a small Linux VM or cloud instance and adding smoke tests for the example service and health script.
