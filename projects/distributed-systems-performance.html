Distributed Systems Performance Lab

A focused backend lab for understanding how caching, database connections, concurrency, and fallback behavior affect latency and reliability.

PythonFastAPIRedisPostgreSQLDocker

01 · Overview

This project explores performance and reliability behavior in a small distributed backend environment. The emphasis is on understanding what changes when caching, pooling, concurrency, and component failures are introduced.

02 · Problem

Backend systems can look healthy in a simple local request path while hiding expensive database work, connection pressure, cache dependency, or poor failure behavior. The lab makes those tradeoffs visible.

03 · Architecture

A FastAPI application works with PostgreSQL and Redis in a Docker-based environment. The lab exercises the system under different data-access and failure paths.

04 · Technical Decisions

  • Redis is used to explore the impact of caching.
  • PostgreSQL provides a realistic persistent data path.
  • Connection pooling and concurrency are treated as system behavior, not only code-level implementation details.
  • Docker keeps dependencies and experiments reproducible.

05 · Reliability / Failure Handling

The lab includes fallback behavior so the application can be evaluated when a dependency such as the cache is unavailable instead of only in the happy path.

06 · Observability

Instrumentation is used to make latency and system behavior easier to compare while running the experiments.

07 · Testing

The repository includes 8 tests covering the lab's application behavior. The benchmark work also exercises database access, pooling, Redis cache hits, concurrency, and Redis-unavailable fallback paths rather than relying on a single happy-path request.

08 · Results

Recorded local benchmark runs measured 223.45 req/s for the PostgreSQL baseline, 640.24 req/s with connection pooling, 652.08 req/s on Redis cache hits, and 395.10 req/s while Redis was unavailable and the application used its fallback path.

These are historical, local, workload-specific measurements from the lab—not production performance guarantees. The current main branch uses the pooling and Redis-first path and does not recreate every earlier baseline configuration by itself.

09 · Lessons Learned

Performance work is most useful when it is connected to reliability: a faster happy path is not enough if the system becomes brittle when a cache or database path changes.

10 · What I Would Change for Production

A production environment would add representative load profiles, longer-running tests, resource limits, production telemetry, and infrastructure that more closely mirrors real deployment constraints.
