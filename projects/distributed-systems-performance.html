01 / Problem

Optimization choices should be measured, not assumed.

The lab uses a small FastAPI item-lookup service to compare how PostgreSQL connection reuse, Redis caching, dependency failure, and concurrency change observable request behavior.

The goal is not to chase the highest local benchmark number. It is to understand which change actually moves the system, what happens to slower requests, and whether the service still behaves predictably when an optional dependency fails.

02 / Request path

The cache is an optimization, not the source of truth.

The current application checks Redis first. A cache hit returns immediately; a cache miss or Redis read error falls through to PostgreSQL. When the database returns an item, the application attempts to cache the result for later requests.

  • Redis hit: return the cached item.
  • Redis miss or error: query PostgreSQL.
  • Database success: return the item and attempt a cache write.
  • Missing item: return HTTP 404.

This makes the dependency hierarchy explicit: Redis can improve the request path, but PostgreSQL remains the authoritative data source.

03 / Experiment design

Change one major system behavior at a time.

The recorded baseline, pooling, and cache-hit experiments each used five runs of 200 measured requests at concurrency 10. Redis-unavailable testing used six runs under the same measured request count and concurrency. All recorded runs reported zero measured request errors.

A separate concurrency experiment tested levels of 1, 10, 25, and 50 to compare how parallelism affected useful throughput and tail latency.

04 / Key finding

Connection pooling produced the largest improvement for this workload.

PostgreSQL baseline223.45 req/s · 44.67 ms avg · 77.22 ms p95
PostgreSQL pooling640.24 req/s · 15.36 ms avg · 28.59 ms p95
Redis cache hits652.08 req/s · 15.38 ms avg · 33.27 ms p95
Redis unavailable395.10 req/s · 24.87 ms avg · 40.82 ms p95

For this small local primary-key lookup workload, connection pooling moved throughput from roughly 223 to 640 requests per second. Redis cache hits produced only a small additional throughput increase over the pooled PostgreSQL path.

05 / Dependency failure

A Redis outage degraded performance without automatically becoming an application outage.

Redis connection and socket timeouts are each configured at 0.1 seconds with retries disabled. That keeps a failed cache operation from holding the request path indefinitely before PostgreSQL fallback is attempted.

During the recorded Redis-unavailable experiment, requests continued through PostgreSQL fallback with zero measured request errors. The fallback still depends on PostgreSQL being healthy, so this is graceful degradation around one dependency rather than full fault tolerance.

06 / Concurrency

More parallelism was not automatically better.

Among the tested concurrency levels of 1, 10, 25, and 50, throughput peaked at concurrency 10. Beyond that point, throughput declined while tail latency increased.

The experiment reinforces an operational point: concurrency should be tuned against actual workload behavior, because additional parallel work can introduce contention instead of producing additional useful throughput.

07 / Observability & verification

Client-side benchmark output is only part of the picture.

The application exposes Prometheus-format metrics at /metrics so dependency and request behavior can be observed from the service itself. The automated suite contains eight tests covering cached responses, PostgreSQL fallback routing, missing items, Redis misses, and Redis read/write errors.

GitHub Actions runs the test suite on pushes and pull requests, keeping failure-path behavior under continuous validation.

08 / Takeaway

Performance engineering is also reliability engineering.

The most useful result was not simply that one configuration was faster. The lab connected connection management, caching, fallback behavior, concurrency, and p95/p99 latency so optimization could be evaluated as system behavior rather than as one average number.

The repeated lesson is: measure first, change deliberately, test failure behavior, and keep the limits of the measurement visible.

09 / Boundary

Local benchmark results are evidence, not capacity claims.

The figures are historical, workload-specific local measurements. Hardware, system load, dataset shape, request mix, and experiment configuration affect the result. The current code always uses connection pooling and checks Redis first, so running the current branch unchanged does not recreate every earlier baseline configuration.

The repository records the methodology and limitations so these results are not presented as production throughput or universal performance claims.
