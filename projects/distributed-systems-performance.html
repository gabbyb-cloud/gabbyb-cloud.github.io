01 / Problem

Optimization choices should be measured, not assumed.

The lab uses a small FastAPI item-lookup service to compare how PostgreSQL connection reuse, Redis caching, dependency failure, and concurrency change observable request behavior.

The goal is not to chase the largest local benchmark number. It is to identify which change actually moves the system, what happens to tail latency, and whether the request path remains predictable when an optional dependency fails.

02 / Architecture

The cache is an optimization; PostgreSQL remains the source of truth.

Requests enter FastAPI and check Redis first. A cache hit returns immediately. A cache miss or Redis read error falls through to a PostgreSQL connection pool. Successful database reads are returned to the client and then written back to Redis when possible.

Cache miss/errorFastAPI → PostgreSQL pool → response
Cache refillDatabase result → best-effort Redis write

03 / Experiment design

Change one major behavior at a time and keep the workload visible.

The recorded baseline, pooled PostgreSQL, and Redis cache-hit experiments each used five runs of 200 measured requests at concurrency 10. The Redis-unavailable experiment used six runs with the same measured request count and concurrency. All recorded runs reported zero measured request errors.

A separate concurrency experiment tested levels 1, 10, 25, and 50. Benchmarks tracked throughput, average latency, p95, p99, and errors so slower requests were not hidden behind a single average.

04 / Key finding

Connection pooling produced the largest improvement for this workload.

PostgreSQL baseline223.45 req/s · 44.67 ms avg · 77.22 ms p95 · 113.41 ms p99
PostgreSQL pooling640.24 req/s · 15.36 ms avg · 28.59 ms p95 · 38.73 ms p99
Redis cache hits652.08 req/s · 15.38 ms avg · 33.27 ms p95 · 48.29 ms p99
Redis unavailable395.10 req/s · 24.87 ms avg · 40.82 ms p95 · 50.54 ms p99

For this local primary-key lookup workload, connection pooling increased throughput from roughly 223 to 640 requests per second while reducing both average and tail latency. Redis cache hits added only a small throughput improvement over the pooled PostgreSQL path.

05 / Dependency failure

A cache outage degraded performance without automatically becoming an application outage.

Redis connection and socket timeouts are set to 0.1 seconds with retries disabled. That bounds how long the request path waits before falling back to PostgreSQL.

During the recorded Redis-unavailable experiment, requests continued through PostgreSQL fallback with zero measured request errors. Throughput dropped and latency rose, but the service remained functional because Redis was designed as optional rather than authoritative.

This is graceful degradation around one dependency, not full fault tolerance: if PostgreSQL fails, the authoritative read path is still unavailable.

06 / Concurrency

More parallelism was not automatically better.

Among concurrency levels 1, 10, 25, and 50, throughput peaked at 10. Beyond that point, throughput declined while tail latency increased.

The result makes concurrency a tuning variable rather than a target. More in-flight work can increase contention and queueing instead of producing useful capacity.

07 / Verification

Performance evidence is paired with deterministic failure-path tests.

The automated suite contains eight tests covering cached responses, PostgreSQL fallback routing, missing items, Redis misses, Redis read errors, and Redis write errors. GitHub Actions runs the suite on pushes and pull requests.

The tests use controlled substitutes for Redis and database operations, so they verify routing and error behavior deterministically. They do not prove real PostgreSQL or Redis availability end to end.

08 / Tradeoffs

Every optimization adds another operating decision.

  • Pooling: removes repeated connection setup cost, but pool size becomes part of capacity behavior.
  • Caching: can reduce database work, but it adds freshness and dependency-management concerns.
  • Fallback: preserves availability during a cache failure, but shifts load back to PostgreSQL.
  • Short timeouts: keep fallback responsive, but can be too aggressive in a slower environment.
  • Concurrency: can increase throughput only until contention and queueing begin to dominate.
09 / What this proved

Performance engineering and reliability engineering overlap.

The useful result is not simply that one configuration was faster. The lab connects connection management, caching, dependency fallback, concurrency, and p95/p99 latency so system changes can be evaluated as operational behavior.

The recurring workflow is: measure first, change deliberately, observe the tails, test failure behavior, and keep the limits of the measurement visible.

10 / Production boundary

Local benchmark results are comparison evidence, not capacity claims.

The recorded figures are short-duration, workload-specific local measurements. Hardware, system load, dataset shape, request mix, pool configuration, and cache behavior all affect the result.

The current code always uses pooling and checks Redis first, so reproducing the historical baseline configurations requires the recorded experiment setup in the repository. A production evaluation would also need real integration tests, longer concurrent load tests, full metrics collection, dashboards, alerting, and SLOs based on observed behavior.
