01 / System goal

Measure system behavior instead of guessing at optimization.

The lab starts with a small FastAPI backend using PostgreSQL and Redis, then changes one system behavior at a time to observe how database connections, caching, concurrency, and dependency failure affect the request path.

The goal is not to produce a universal benchmark. It is to connect implementation choices to measured behavior and understand the tradeoffs behind them.

02 / Request path

A small path with meaningful dependencies.

The current application checks Redis first. Cache hits return immediately; cache misses or Redis errors fall through to PostgreSQL. Successful database results are then eligible to be cached for subsequent requests.

  1. Check Redis for the requested item.
  2. Return a cache hit when available.
  3. On miss or Redis error, query PostgreSQL.
  4. Return the database result and attempt to cache it.
03 / Experiment design

Compare baseline, pooling, caching, and failure paths.

Recorded experiments used 200 measured requests per run at concurrency 10. Baseline, pooling, and cache-hit tests used five runs each; Redis-unavailable testing used six. All recorded runs reported zero measured request errors.

A separate concurrency experiment compared levels of 1, 10, 25, and 50 to observe throughput and tail-latency behavior as parallelism increased.

04 / Recorded results

Pooling produced the largest improvement in this workload.

PostgreSQL baseline223.45 req/s · 44.67 ms average
PostgreSQL + pooling640.24 req/s · 15.36 ms average
Redis cache hits652.08 req/s · 15.38 ms average
Redis unavailable395.10 req/s · 24.87 ms average

Connection pooling delivered the largest improvement in the recorded experiments. Redis added relatively little for the small local primary-key lookup workload, while the Redis-outage path continued serving requests through PostgreSQL fallback.

05 / Reliability behavior

Performance matters most when failure behavior remains acceptable.

Redis is configured with short connection and socket timeouts and retries disabled so cache failure does not stall the request path indefinitely. Fallback depends on PostgreSQL remaining available, making the dependency boundary explicit rather than pretending the cache is optional under every condition.

In the concurrency experiment, throughput peaked at concurrency 10 among the tested levels. Higher concurrency increased tail latency while throughput declined, showing that more parallelism was not automatically better for this local workload.

06 / Engineering takeaway

Optimization should be tied to evidence and failure cost.

The lab reinforced that the fastest happy path is not the only useful result. Connection management, cache dependency, fallback timing, and tail latency all affect whether an optimization improves the system as a whole.

07 / Measurement boundary

Local benchmark data needs context.

The figures are historical, workload-specific local measurements. Hardware, system load, and experiment configuration affect the numbers, and the current main branch always uses connection pooling and the Redis-first path.

The repository preserves recorded experiment configurations and results, but running the current application unchanged does not recreate every earlier baseline condition.
