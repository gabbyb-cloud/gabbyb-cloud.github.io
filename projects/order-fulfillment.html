Order Fulfillment with Temporal

A backend project focused on durable execution: workflows that can retry, compensate, persist state, and recover from process failure without losing the business operation.

PythonFastAPITemporalPostgreSQLDocker

01 · Overview

The project models an order-fulfillment workflow using Temporal with a FastAPI-facing backend and PostgreSQL persistence. It emphasizes workflow durability rather than a conventional request/response-only architecture.

02 · Problem

Multi-step order workflows fail in messy ways: a process can crash, an external step can time out, or a later step can fail after earlier work already succeeded. The project explores how durable workflows make those failures explicit and recoverable.

03 · Architecture

FastAPI accepts work at the application boundary, Temporal coordinates long-running workflow execution, activities perform individual steps, and PostgreSQL supports the surrounding persisted application state.

04 · Technical Decisions

  • Temporal provides durable workflow state and controlled retries.
  • Saga-style compensation provides a structured path for undoing completed work when a later step fails.
  • Docker makes the local multi-service environment reproducible.
  • Integration testing and CI exercise failure and recovery behavior continuously.

05 · Reliability / Failure Handling

The design focuses on retries, compensation, and crash recovery so a worker or process interruption does not automatically mean losing workflow progress.

06 · Observability

Temporal makes workflow state and failures inspectable rather than burying them inside ad-hoc background jobs, and the application adds structured logging around the API and workflow path.

07 · Testing

The repository includes 8 passing tests covering important workflow behavior and recovery paths, with CI used to validate the project automatically. The API also includes API-key authentication for the implemented local application boundary.

08 · Results

The project demonstrates a working durable-execution approach for multi-step backend work, including retries with backoff, Saga-style compensation, cancellation, persistence, and worker-crash recovery. A local benchmark completed 25 of 25 requests successfully at about 30 ms average latency and about 49 ms p95.

Benchmark figures are local, workload-specific measurements and are not production throughput or latency guarantees.

09 · Lessons Learned

Durable workflow tooling changes how backend failures are modeled: rather than treating background work as disposable, the workflow itself becomes explicit state that can survive process interruptions.

10 · What I Would Change for Production

A production version would move beyond the current API-key boundary to managed identity and authorization, add managed secrets, environment-specific deployment, capacity planning, deeper telemetry, and externally managed infrastructure.
