Order Fulfillment with Temporal

A multi-step order workflow designed so execution remains predictable when work is interrupted or a later step fails: persist state, classify failure, retry safely, compensate when necessary, resume execution, and verify behavior.

01 / Problem

A long-running business process cannot depend on one worker staying alive.

Order fulfillment spans several steps that can succeed or fail independently. If workflow progress exists only in process memory, a worker crash can turn an infrastructure interruption into lost business state.

This project models the order as durable workflow state so payment validation, inventory reservation, shipping, and notification can be coordinated independently of the lifetime of one API or worker process.

02 / Architecture

API submission is separated from durable execution.

FastAPI accepts the request and starts the workflow. Temporal owns workflow history and coordinates execution, while workers perform the individual activities. PostgreSQL supports persisted application data, and Docker Compose provides a reproducible local environment.

  • FastAPI: authenticated API boundary for starting and querying orders.
  • Temporal: durable workflow history, retries, cancellation, and execution recovery.
  • Activities: payment, inventory, shipping, and notification work.
  • PostgreSQL: persisted application state.
  • GitHub Actions: automated verification on repository changes.
03 / Failure classification

Not every failure should receive the same response.

Transient infrastructure failures use bounded retries with exponential backoff because another attempt may succeed. Business conditions such as invalid payment details, unavailable inventory, or an invalid shipping address are treated as non-retryable because repeating the same work would not fix the underlying condition.

Making that distinction explicit prevents retry policy from becoming a blanket response to every error.

04 / Partial completion

Successful earlier steps need an explicit recovery path.

If shipping fails after payment and inventory reservation have already succeeded, the workflow compensates in reverse order: release the inventory, then refund the payment.

Cancellation is also handled at defined checkpoints so completed work can be compensated and later work can be prevented from starting unnecessarily.

05 / Crash recovery

Worker interruption is exercised directly.

A controlled worker restart demonstrates that workflow history remains durable while the worker is unavailable. When the worker returns, execution can continue from persisted workflow state instead of reconstructing the order from memory or restarting the entire business process.

The reliability property being tested is simple but important: workflow progress outlives the worker process.

06 / Verification

Failure behavior is part of the test suite.

The automated suite contains 11 passing tests covering workflow and API behavior, including transient failures, non-retryable business failures, shipping compensation, cancellation checkpoints, authenticated API access, and status queries.

This keeps recovery behavior testable instead of treating it as an architectural assumption.

07 / Measured result

The benchmark measures submission, not end-to-end fulfillment.

An example local run completed 25 of 25 authenticated order submissions successfully, with an average submission latency of 38.74 ms and p95 of 75.51 ms.

These figures are local, workload-specific measurements of order submission inside the Docker Compose environment. They are not production-capacity claims and do not measure complete workflow duration.
08 / Takeaway

Reliable background work needs explicit state and explicit recovery.

Durable execution makes retry policy, business failures, compensation order, cancellation points, and crash recovery visible parts of system behavior. The main lesson is not simply how to use a workflow engine; it is how to design work so failure paths are predictable and testable.

09 / Boundary

The project proves workflow behavior, not a production commerce platform.

Payment, inventory, shipping, and notification integrations are intentionally simulated. A production implementation would still need real external integrations, stronger end-to-end idempotency guarantees, managed identity and secrets, distributed tracing, production alerting, higher-volume load testing, and dependency-specific SLOs.
