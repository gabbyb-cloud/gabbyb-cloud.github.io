Case Study 02 · Durable Backend Workflows

Order Fulfillment with Temporal

A backend system for multi-step order processing where workflow state survives process interruption and failures are handled through bounded retries, compensation, persistence, and explicit recovery behavior.

01 / System goal

Keep business work durable when processes fail.

Order fulfillment is modeled as a long-running workflow rather than a chain of fragile request/response calls. FastAPI accepts the request, Temporal owns workflow state and execution history, and workers perform payment, inventory, shipping, and notification activities.

The core question is not whether every step succeeds immediately. It is whether the system can represent retries, business failures, partial completion, cancellation, and worker interruption without losing the operation.

02 / Architecture

Separate API submission from durable execution.

The API starts a workflow and returns while Temporal coordinates the longer-running state machine. PostgreSQL supports persisted application state and Docker Compose makes the multi-service environment reproducible.

  • FastAPI defines the external application boundary.
  • Temporal persists workflow history across worker restarts.
  • Activities isolate payment, inventory, shipping, and notification work.
  • PostgreSQL provides persisted application data.
  • Docker Compose packages the local development environment.
03 / Failure model

Not every failure should be retried.

Transient infrastructure failures use bounded retries with exponential backoff, while invalid cards, unavailable inventory, and invalid addresses are treated as non-retryable business failures.

When a later step fails after earlier work completed, compensation runs in reverse order. Payment can be refunded, inventory can be released, and cancellation is handled at defined checkpoints so later work does not continue unnecessarily.

04 / Recovery & verification

Crash recovery is part of the project, not an assumption.

A controlled worker restart demonstrates that workflow execution can resume from durable history rather than restarting the business operation from scratch. Automated tests cover workflow and API behavior, including compensation and cancellation paths, and GitHub Actions validates the project continuously.

05 / Measured result

Measure the submission path without overstating it.

A local benchmark run completed 25 of 25 authenticated order submissions successfully. The measured average submission latency was 38.74 ms and p95 was 75.51 ms.

These figures measure local order submission inside the Docker Compose environment. They do not represent complete workflow duration, production-scale load, or a performance guarantee.
06 / Engineering takeaway

Durable execution changes the shape of backend failure handling.

Background work becomes explicit workflow state instead of disposable process state. That makes retry policy, compensation order, cancellation points, and recovery behavior inspectable and testable rather than hidden in ad-hoc jobs.

07 / Production boundary

The local architecture proves behavior, not production readiness.

A production version would replace the current API-key boundary with managed identity and authorization, move secrets into managed storage, add environment-specific deployment, deeper telemetry, capacity planning, and externally managed infrastructure.
