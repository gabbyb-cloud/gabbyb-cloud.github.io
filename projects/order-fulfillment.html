Case Study 03 · Backend Reliability

Order Fulfillment with Temporal

A durable order-processing workflow built to make failure behavior explicit: persist workflow state, distinguish retryable from non-retryable failures, compensate partial success, handle cancellation safely, survive worker restarts, and verify recovery paths with tests.

01 / Problem

A multi-step business process cannot depend on one worker process staying alive.

Order fulfillment spans several operations that can succeed or fail independently. Payment can succeed before inventory fails. Inventory can be reserved before shipping fails. A worker can stop midway through the process.

If workflow progress exists only in memory, infrastructure failure can become lost business state. This project moves execution state into Temporal so workflow progress can outlive the API and worker processes that happen to be running at any moment.

02 / Architecture

Request handling is separated from durable execution.

FastAPI receives authenticated order requests and starts Temporal workflows. Temporal persists execution history independently of the worker process, and the worker executes payment, inventory, shipping, and notification activities. PostgreSQL supports persisted application data, while Docker Compose keeps the local environment reproducible.

Entry pointClient → FastAPI → Temporal workflow
Durable stateTemporal stores workflow history outside worker memory
ExecutionWorker runs payment, inventory, shipping, notification activities
PersistencePostgreSQL supports application state in the local stack
03 / Failure classification

Retry policy starts by deciding which failures can actually improve with another attempt.

Transient infrastructure failures use bounded retries with exponential backoff because another attempt may succeed. Business failures such as invalid payment details, unavailable inventory, or an invalid shipping address are marked non-retryable because repeating the same activity does not change the underlying condition.

This keeps retry behavior intentional instead of treating every exception as a reason to try again.

04 / Partial completion

Every successful side effect needs a recovery plan if later work fails.

The workflow uses Saga-style compensating actions rather than pretending several external operations can be rolled back atomically. If shipping fails after payment and inventory reservation succeed, compensation runs in reverse order: release the inventory, then refund the payment.

Shipping failureRelease inventory → refund payment
Cancel after paymentCompensate payment and prevent later work
Cancel after inventoryRelease inventory → compensate payment
GuaranteeCompensation order is asserted by automated tests

Compensation is explicit business logic, not the equivalent of an atomic database rollback. That distinction is important because external side effects can have their own failure modes.

05 / Cancellation

Cancellation is accepted at controlled checkpoints.

The workflow checks for cancellation at defined points so completed work can be compensated when necessary and later activities can be prevented from starting. This favors predictable recovery semantics over attempting to interrupt arbitrary work at any instant.

The test suite verifies cancellation after payment and after inventory reservation, including the expected compensation path for each state.

06 / Crash recovery

Worker failure does not erase workflow progress.

A controlled worker restart exercises the core durability property directly. While the worker is unavailable, Temporal retains workflow history. When the worker returns, execution can continue from persisted workflow state instead of reconstructing the order from process memory or starting the entire business process over.

The reliability property being tested is simple: workflow state outlives the worker that executes it.

07 / Verification

Failure paths are treated as testable system behavior.

The automated suite contains 11 passing tests covering successful execution, transient retries, non-retryable business failures, compensation after shipping failure, cancellation checkpoints, authenticated API behavior, and workflow status queries.

08 / Measured result

The local benchmark measures API submission only.

One local Docker Compose run completed 25 of 25 authenticated order submissions successfully, with an average submission latency of 38.74 ms and p95 submission latency of 75.51 ms.

These measurements cover sequential order submission in the local environment. They are not production-capacity claims, do not measure complete workflow duration, and will vary by hardware and system load.
09 / Reliability tradeoffs

Durable orchestration solves some failure problems, not all of them.

Temporal gives the workflow durable history and repeatable orchestration, but real external side effects would still require stronger idempotency guarantees. A retry against a payment or shipping provider must not accidentally duplicate the side effect simply because the workflow itself is durable.

The project also emits structured operational events, but it does not yet include distributed tracing, production alerting, or dependency-specific SLOs.

10 / What this proved

Reliable background work needs explicit state, explicit failure semantics, and explicit recovery.

The project demonstrates a backend design where retry policy, business failures, compensation order, cancellation checkpoints, and worker crash recovery are visible parts of system behavior rather than hidden assumptions.

The central lesson is not simply how to use Temporal. It is how to design multi-step work so failure paths remain understandable, recoverable, and testable.

11 / Production boundary

This proves workflow behavior, not a production commerce platform.

Payment, inventory, shipping, and notification integrations are simulated intentionally so the project can isolate workflow durability and failure handling without third-party credentials or sandboxes.

A production implementation would still need real external integrations, end-to-end idempotency controls, managed identity and secrets, distributed tracing, production alerting, larger concurrent load and recovery tests, and SLOs derived from measured dependency behavior.
